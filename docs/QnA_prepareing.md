# 발표 예상 QnA — 밤마실

> 스토리보드(발표 대본) 기준 예상 질의응답. **우선순위는 스토리보드가 이미 그 내용을 언급했는지**
> 분석 포인트는 `docs/STATUS.md` 실측 수치 근거.

- 🔴 **상** — 스토리보드 미언급. 심사에서 새로 파고들 가능성이 높은 항목. 우선 대비.
- 🟡 **중** — 스토리보드가 결론만 짧게 언급. 근거·디테일을 되물을 가능성.
- 🟢 **하** — 스토리보드가 이미 질문-답 형태로 다룸. 같은 질문이 그대로 나올 가능성은 낮음(단, 반박형으로 재구성돼 나올 순 있음).

## 🔴 상 — 우선 대비 (대본에 없는 내용)

**Q5. 학습 데이터가 해외 위주인데 실제 한국 야간 환경에 맞나요?**
- 대본은 데이터 출처(3개국 야간 주행, StairNet, AIHub)만 나열할 뿐 국내 적합성·촬영 시점 불일치는 언급 안 됨
- NightOwls는 차량 대시캠 시점이라 보행 시점과 다름
> **예시 답변:** "실제 국내 야간 보행 환경에서 직접 촬영한 자체 데이터로 별도 검증을 진행하였습니다."

**Q9. 검증에 쓴 사진들, 사람이 직접 라벨링했나요?**
- 대본에 라벨링 주체 언급 없음
- 핵심 학습 데이터(NightOwls·AIHub·StairNet)는 원본 사람 손 라벨. 자체 촬영 검증 데이터는 팀이 직접 라벨링(육안 근사).
> 학습 데이터는 수동 라벨링 되어 있는 공개 데이터를 사용했고 직접 촬영한 검증용 데이터는 팀원이 손수 라벨링했습니다.

**Q15. 화면에 표시만 하고 음성 경고는 안 주는데, 사용자가 못 보고 지나칠 위험은 없나요?**
- 대본은 "직접 확인·판단"을 강점으로만 제시하고, 놓칠 위험에 대한 반박은 없음 — 날카로운 질문으로 나올 가능성 높음
- 설계 철학상 과도한 자동 경고는 오탐 시 신뢰를 해친다고 판단해 시각 강조를 택함. 향후 음성/진동 보조 알림을 옵션으로 추가하는 방향도 검토 중이라는 여지를 남겨 답변
> **예시 답변:** 

**Q16. 색상으로 위험요소를 구분하는데, 색약이 있는 저시력자는요?**
- 대본에 색각이상 언급 전혀 없음 — 접근성에 민감한 심사위원이면 반드시 나올 질문
> 추후에 여러 색상 조합을 제시해 해결할 계획입니다.

**Q18. 검증에 쓴 자체 촬영 데이터의 규모와 분포가 어떻게 되나요?**
- 대본은 촬영 표본 규모를 전혀 언급하지 않고 수치만 제시 — 데이터 규모를 캐묻는 질문은 거의 확실히 나옴
- 현재 수치는 "1차 판정" 성격임을 인정하고, 정규 촬영 → 기관 실증으로 확대하는 로드맵으로 방어
> 약 120장(구라)의 실제 촬영 이미지를 사용하였습니다. 

**Q19. mAP·recall 같은 지표가 실제 야간 이동 안전성과 어떻게 연결되나요?**
- 대본은 지표를 결과로만 제시하고 안전성과의 연결고리는 설명하지 않음
- mAP·recall은 위험요소를 놓치지 않는 정도의 대리 지표이며, FSM 잔상 감소·실기기 FPS·사용자 인터뷰로 실사용성을 보완
> 실제 사용 시에는 연속된 영상이기 때문에 여러 프레임에 걸쳐 탐지를 시도합니다. 이로 인해 실사용 시에는 지표에 비해 더 좋은 탐지 결과를 체감할 수 있습니다.

**Q22. 경쟁사나 특허 이슈는 검토했나요?**
- 대본에 전혀 없는 영역 — 사업성 심사에서 나올 수 있음
- 특허 출원 조사는 미실시. 라이선스 이슈는 일부 확인됨 — YOLO(Ultralytics)는 AGPL-3.0(상용화 시 상업 라이선스 전환 필요), 학습에 쓴 NightOwls는 비상업 전용(→ `docs/data.md` 5장·858-866행). 직접 경쟁사 비교는 문서에 없고, README의 확대독서기 비교는 카테고리가 다른 제품과의 경제성 비교일 뿐 경쟁사 분석은 아님
> 추후 자체 데이터 사용해서 데이터 라이선스 해결 예정.

## 🔴 상 — 모델 관련 추가 (대본 미언급, 우선 대비)

**Q28. 계단 클래스만 유독 성능(AP50 0.12~0.20)이 낮은데, 더 학습시키면 해결되나요?**
- 대본 15번은 3클래스 통합 mAP(0.571)만 제시하고 클래스별 약점(특히 계단)은 전혀 언급하지 않음 — 통합 수치 뒤에 숨은 약점을 캐묻는 질문으로 나올 가능성 높음
- 정량 분석: 학습 데이터(StairNet)의 계단 박스는 화면의 중앙값 47.5%를 차지하는 근접샷 위주인 반면, 실제 보행 중 계단 GT 박스는 중앙값 약 3.0%(71%가 화면의 10% 미만)로 훨씬 작고 멀리 있음
- 즉 모델이 실제 보행 시 계단이 보이는 스케일을 거의 학습한 적이 없는 **스케일·도메인 갭** 문제로 확인됨 — 양자화·증류·추가 에폭으로 해결될 문제가 아니라, 거리별 실촬영 데이터 확충이 필요 (`docs/model_selection.md` §8-5)
> 학습 데이터와 실제 환경의 차이입니다. 학습 데이터는 대부분 계단을 근접해서 촬영하였기에 계단이 멀리서 촬영되는 실제 환경의 경우와 차이가 있었습니다. 이에 대해서는 추후 실제 데이터를 추가하여 해결할 계획입니다.

> **정확한 이유:** 학습에 쓴 StairNet 계단 박스는 화면의 중앙값 47.5%를 차지하는 근접샷 위주인 반면, 실제 보행 중 계단 GT 박스는 중앙값 약 3.0%(71%가 화면의 10% 미만)로 훨씬 작고 멀리 있음 — 즉 모델이 실제 보행 시 계단이 보이는 스케일 자체를 거의 학습한 적이 없는 스케일·도메인 갭이며, 라벨 품질이나 모델 성능(양자화·증류·추가 에폭)의 문제가 아니어서 거리별 실촬영 데이터 확충 외에는 근본 해결책이 없음.

**Q29. INT8 양자화를 QDQ·Static 방식으로 한 이유는요? 다른 양자화 방식은 검토 안 했나요?**
- 대본은 "지식증류 후 양자화로 크기를 90% 축소"라고만 언급하고, 양자화의 세부 방식(QDQ vs QOperator, Static vs Dynamic)은 전혀 다루지 않음 — 기술 심사에서 세부 구현을 캐물으면 바로 나올 수 있는 질문
- ⚠️ 본 프로젝트는 NPU가 없는 저사양 기기도 타깃으로 하므로, "모바일 NPU가 고정 스케일을 요구해서"처럼 NPU 존재를 전제로 한 근거는 부적절함 — NPU 유무와 무관하게 성립하는 근거로 답해야 함
> **Static을 쓴 이유** (dynamic 대신): 이 모델은 CNN(Conv 88개)이라 캘리브레이션으로 활성값 범위를 미리 고정하는 게 정확도·속도 면에서 정석입니다. 게다가 dynamic은 매 추론마다 활성값 범위를 새로 계산해야 하는데, 이 반복 연산 자체가 저사양 기기에서 부담이 됩니다. 즉 저사양 기기까지 커버해야 하는 저희 상황에서 static이 더 유리합니다.
> **QDQ 형식을 쓴 이유** (QOperator 대신): QDQ ONNX는 런타임 중립적인 표준 포맷이라, 즉 하드웨어 구성과 무관하게 대응할 수 있는 높은 호환성을 가지기 때문입니다. 사실상 CPU 전용 포맷인 QOperator 대신 QDQ를 택한 이유입니다.

## 🟡 중 — 모델 관련 (대본이 결론만 언급, 근거·디테일을 되물을 가능성)

**Q23. 왜 YOLO11n을 선택했나요? 더 크거나 최신 모델(YOLO26 등)은 검토 안 했나요?**
- 대본 9번(모델)에서 "모델과 입력 해상도를 여러 조건으로 비교했고, 정확도와 모바일 구동 비용을 함께 고려해 YOLO11n 640을 사용"이라고 결론은 이미 언급함 — 다만 어떤 모델을 비교했고 왜 YOLO26n은 탈락했는지 구체적 근거는 대본에 없어, 같은 질문이 그대로 나올 가능성은 낮고 "구체적으로 뭘 비교했나요?" 식 후속 질문으로 나올 가능성이 있음
- 온디바이스(스마트폰 단독, 서버 없음) 720p·15FPS 예산이 모델 크기·입력 해상도·양자화를 동시에 제약
- YOLO26n은 주간 소형 볼라드(<4px) recall이 +0.124 더 높았지만, 야간 held-out 게이트(person recall ≥0.609)를 통과 못함(0.594)에다 NMS-free 구조라 앱의 고정 출력 계약이 깨져 최종 탈락 (`docs/model_selection.md` §2-1)
> 모바일 온디바이스에서 '실시간' 탐지를 가능하게 하기 위해서는 지금 모델보다 더 큰 모델을 선택하기 어려웠습니다. 또한 기존 베이스라인 실험에서 사용한 모델과 출력 포멧이 달라 호환성이 떨어졌고 성능 게이트를 26n이 넘지 못하여 선택하지 않았다.

> **정확한 이유:** 온디바이스(스마트폰 단독, 서버 없음) 720p·15FPS 예산이 모델 크기·입력 해상도·양자화를 동시에 제약하는 상황에서, YOLO26n은 주간 소형 볼라드(<4px) recall이 +0.124 더 높았음에도 (1) 야간 held-out 게이트(person recall ≥0.609)를 통과 못함(0.594)했고 (2) NMS-free 구조라 디코딩·후처리를 앱이 직접 맡아야 해 기존 고정 출력 계약(ONNX 형태)이 깨져, 두 조건 모두 탈락 사유로 겹쳤음.

**Q25. 왜 모델 전체가 아니라 일부만 양자화했나요?**
- 왜 전체가 아니라 Conv 레이어만 양자화했는지(Concat 스케일 붕괴) 같은 기술적 근거는 대본에 없어 되물을 가능성이 있음
- 전체 그래프 양자화 시 마지막 Concat 레이어가 박스좌표(0~640)와 클래스 점수(0~1)를 한 텐서로 합쳐 공유 스케일이 깨지며 탐지 결과가 전부 0으로 붕괴 (`docs/STATUS.md` "Pitfall 20")
- Conv 레이어만 양자화하는 방식으로 우회 → 10.61MB→3.15MB(3.37배 압축), 야간 볼라드 탐지 유지(2/2 검출). INT4·FP8은 테스트 후 기각(정확도 붕괴/실행 미지원)
> 전체를 양자화하면 모델의 출력 구조 스케일이 깨져 탐지 기능이 실패하는 것을 확인했습니다. 그래서 합성곱 레이어만 선택적으로 양자화하였습니다.

> **정확한 이유:** 모델의 마지막 Concat 레이어가 박스좌표(0~640 범위)와 클래스 점수(0~1 범위)를 하나의 출력 텐서로 합치는데, 전체를 INT8로 양자화하면 이 두 값이 하나의 공유 uint8 스케일을 강제로 나눠 써야 해서 스케일이 붕괴하고 탐지 결과가 전부 0으로 나옴 — 그래서 이 Concat 이전의 합성곱(Conv) 레이어만 양자화해 우회했고, 그 결과 10.61MB→3.15MB(3.37배 압축)로도 야간 볼라드 탐지(2/2)를 유지함. INT4·FP8도 시도했으나 각각 정확도 붕괴·실행 미지원으로 기각.
