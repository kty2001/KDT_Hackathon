# ③ 탐지 모델 선택 근거 — `YOLO11n` · `640` · INT8 양자화 · 증류

## 0. 결론 요약

이 프로젝트는 **서버 없이 스마트폰 단독으로 720p·15FPS**를 내야 한다는 단일 제약에서
출발했고, `③ 탐지`가 쓸 수 있는 시간 예산은 `② 저조도 개선`이 이미 상당 부분을 먹은
나머지다. **이 FPS 예산 하나가 모델 크기(`YOLO11n`)·입력 해상도(`640` 고정)·경량화
(INT8 양자화)·정확도 보완 수단(증류) 네 가지 결정을 전부 지배한다.**

| 선택 | 지배 원리 |
|---|---|
| **모델 = `YOLO11n`** | 모바일 온디바이스 FPS 예산이 nano 급만 허용 |
| **입력 해상도 = `640` 고정** | ②가 이미 예산 대부분을 소비 · 960은 실기기 미검증이라 근거 없이 못 올림 |
| **양자화 = INT8(Conv만)** | 같은 640·같은 11n을 더 작게(3.15MB) — 배포 크기 압축 |
| **증류 = `11s`→`11n`** | 640·11n을 유지한 채 정확도만 끌어올림 — 960이 못 푸는 `<4px` 문제를 해상도 대신 용량으로 공략 |

✅ **이 네 가지가 합쳐진 최종 배포판은 `c4f_distill_11n_640` INT8이다 — 2026-09-03 팀 채택
확정**(→ 7장 · [STATUS.md 갱신 박스](STATUS.md)). ⚠️ 다만 이 논리의 최종 전제인 **실기기
속도 계측(`C11`/`C11b`)은 아직 안 끝나** 있어(→ 6장) 위 판단은 그 계측 전까지 최선 판단이다.

## 1. 배경 제약 — 왜 하나의 FPS 예산이 전부를 묶는가

- **프로젝트 요구사항**: 추가 하드웨어 없이 스마트폰 단독 동작, 영상 처리·추론 전부
  기기 내에서 수행(서버 전송 없음), 목표 720p·15FPS (→ [README.md](../README.md)).
- **런타임 제약**: TensorRT는 스마트폰에서 동작하지 않아 모바일 런타임(ONNX Runtime +
  QNN/NNAPI/Core ML)으로 온디바이스 추론해야 한다 (→ [hardware_inference.md 1장](hardware_inference.md)).
- **표시/탐지 2경로 분리**(`C7`, 8/2): ②(저조도 개선)는 표시 경로에만 걸리고 ③(탐지)은
  원본 프레임을 받는다. 두 경로가 독립이라 병렬화 가능하지만, ②의 지연 자체는 줄지
  않는다 — 그리고 ②가 640×360 환산 **≈20.4ms**로 이미 속도 게이트 경계선에 있다
  (→ [STATUS.md 1장](STATUS.md)). `③`이 추가로 예산을 더 쓰려면(예: 해상도 960) 근거가
  필요한 상태다.

## 2. 왜 `YOLO11n`인가

- `hardware_inference.md` 2장: `YOLOv8n/v11n(nano)` 320~640 입력 + INT8 양자화 조합이
  "최신 플래그십 NPU 30~60FPS, 중급기도 15FPS" 확보 가능 — 목표 720p 15FPS를 여유 있게
  만족하는 유일하게 검증된 조합.
- `C4` baseline 학습 설정표에 명시: "모델 = YOLO11n (2,590,230 params · 6.4 GFLOPs) —
  근거: **배포 타깃과 일치, FPS 예산이 nano+INT8 전제**" (→ [detection.md 3장](detection.md#3-c4-baseline-학습-scriptstrain_detectpy)).
- **단일 모델 원칙**: `stairs`를 별도 모델로 구동하는 대신 보행자 모델에 클래스로
  통합 — 클래스 1개 추가는 추론 비용이 사실상 0이라 FPS 예산이 오히려 늘어난다
  (→ [detection.md 1장](detection.md#1-왜-단일-모델인가)).

### 2-1. 참고 — 왜 `26n`이 아닌가 (더 작고 소형 물체에 강한 대안인데도)

`YOLO26n`은 `11n`보다 파라미터가 오히려 적으면서(2.50M < 2.59M) 주간 `<4px` 초소형
볼라드 recall이 훨씬 높다(0.443 vs 0.319, **+0.124**) — 이건 용량이 아니라 **구조
(아키텍처) 차이**에서 온 이득이다 (→ [review_response_20260825.md](review_response_20260825.md)).
그런데도 채택하지 않은 이유는 두 가지다.

1. **야간 held-out 게이트를 스스로 탈락했다.** NightOwls `rec34` 평가에서
   `c4d_26n_640`은 person recall **0.594**로 게이트(0.609) 미달 — `❌ 기각`
   (→ [detection.md 9-2·9-3](detection.md#9-2-결과--person-rec-34)). 주간 `<4px` 최강
   모델이 야간에서는 4런 중 꼴찌로 추락한 것으로, **"주간 mAP로 야간 순위를 예측할 수
   없다"는 반복 함정(→ [STATUS.md 3장 함정 1](STATUS.md))의 세 번째 증거**가 됐다.
2. **NMS-free라 배포 계약이 바뀐다.** 현재 배포 계약은 ONNX가 NMS를 제외한 고정
   포맷을 출력하고 앱은 그대로 그려 쓰는 구조인데, `26` 계열은 원출력을 앱 쪽에서
   직접 NMS 처리해야 해 인터페이스 계약 자체가 변경된다 — 앱 구현이 아직 0건인
   상태에서 계약을 먼저 바꾸는 위험을 지지 않기로 했다 (→ [distillation_plan_20260829.md
   3장](distillation_plan_20260829.md), [TODO.md](TODO.md)).

같은 이유로 증류 교사 후보에서도 배제됐다 — `26` 계열은 헤드 구조가 달라 `11n`과 같은
증류 훅이 걸리지 않는다(→ 5장). 즉 `26n`은 **성능 게이트 탈락 + 계약 비용**이라는
이중 이유로 제외됐고, `P3`(앱 골격) 완료 후에만 재고 대상이다.

#### 수치 근거 — 주간에서는 우세, 야간 게이트에서 뒤집힌다

같은 640 입력·50epoch·같은 데이터(`bollard_val_2146`, 볼라드 GT 6,988박스) 기준
**주간 단독 비교**:

| 런 | params | `<4px` recall(GT 22%) | 전체 recall | 데스크톱 inf(ms) |
|---|---|---|---|---|
| `c4d_11n_640` | 2.59M | 0.319 | 0.642 | 1.00 |
| `c4d_26n_640` | **2.50M**(더 적음) | **0.443**(+0.124) | 0.666 | 1.31 |

conf 0.25 스윕에서도 `26n`이 bollard recall(0.666>0.642)·FP(925<1,221) 둘 다 `11n`보다
우세 — **주간 데이터만 보면 `26n`이 명백히 더 나은 선택지였다.**

그러나 **야간 held-out(`rec34`)에서는 순위가 뒤집힌다** — 게이트는 person recall
≥ **0.609**(현 배포 `c4b_loli0` 기준) · `stairs` 오탐 ≤ 0.2%:

| 런 | 야간 mAP50 | Δ(vs 배포) | 야간 recall | Δ | precision | 게이트 |
|---|---|---|---|---|---|---|
| `c4d_11n_640` | 0.736 | +0.052 | **0.644** | +0.035 | 0.789 | ✅ 통과 |
| `c4d_26n_640` | 0.668 | **−0.016** | **0.594** | **−0.014** | 0.821 | ❌ **기각**(0.609 미달) |

**주간→야간 순위 역전**:

| 런 | 주간 mAP50 · 순위 | 야간 mAP50 · 순위 |
|---|---|---|
| `c4d_26n_640` | 0.775 · **2위** | 0.668 · **4위(꼴찌·게이트 기각)** |
| `c4d_11n_640` | 0.753 · 4위(꼴찌) | 0.736 · **2위** |

주간 2등이 야간 꼴찌로, 주간 꼴찌가 야간 2등으로 **거의 정확히 뒤집혔다.** `11n`을
`26n`보다 선택한 이유는 "`11n`이 원래 더 좋아서"가 아니라, **`26n`이 주간에서 보인
구조적 우위(+0.124)가 실제 배포 도메인인 야간에서는 재현되지 않고 배포 게이트 자체를
통과하지 못했기 때문**이다.

## 3. 왜 `640`인가 (960이 아니라)

### 3-1. 속도 예산 근거
- ②가 이미 예산 대부분을 소비하고, **960은 픽셀 2.25배**인데 **실기기 계측이 아직
  없다**(`C11b` 미착수). "근거 없이 올리면 FPS 게이트가 깨진다"는 게 `TODO.md`에 명시된
  판단이다 (→ [TODO.md — C4e 절](TODO.md)).
- 이 전제에 따라 **640을 배포 해상도로 고정**하고, 이후 모든 후보 비교(외부 인수분
  `c4d` 6런, 자체 재학습 `C4e`)는 **640 축 4런만** 평가 대상으로 삼았다 — `960` 런
  2개(`c4d_26n_960` 등)는 "배포 전제 조건이 다르다"는 이유로 판정에서 아예 제외했다
  (→ [detection.md — S0 절](detection.md)).

### 3-2. 데이터 근거 — 960이 실제로 풀려던 문제를 못 푼다
외부 인수분 6런 비교(`R1`)에서 해상도를 올리면 성능이 오르는 건 맞다(같은 50epoch
기준 +0.065, 모델 세대 축 +0.022의 3배). 하지만 정작 겨냥하던 **`<4px` 초소형
볼라드(GT의 22%)는 960으로 올려도 recall 0.49가 상한**이라 해상도로는 더 못 간다
(→ [STATUS.md — 외부 인수분 R1](STATUS.md#r1-6런에서-확정된-것-공식-지표-benchmark_c4dcsv--평가셋-bollard_val_2146)).

반면 같은 640 입력에서 **모델 용량만 올렸을 때**(`11n`→`11s`) `<4px` recall이 **+0.093**
오른다 — `26n`을 640→960으로 올렸을 때 이득(+0.048)보다 **용량 축이 더 싸게 먹힌다**는
게 실측으로 확인됐다 (→ [review_response_20260825.md](review_response_20260825.md)).

**결론**: 해상도를 올리는 것(960)은 ① FPS 예산을 검증 없이 깨는 위험을 지면서도
② 정작 풀려던 소형 물체 문제는 못 푼다. 이 두 가지 이유로 **해상도 축(960)을 포기하고
용량 축(증류)을 택했다** (→ 5장).

## 4. 양자화(INT8) — 같은 640·11n을 더 작게

- Conv 레이어만 INT8 양자화(`op_types_to_quantize=["Conv"]`)해 10.61MB → **3.15MB**
  (3.37배 압축), 야간 볼라드 검출 유지(2/2). 머리의 마지막 `Concat`이 좌표(0~640)와
  점수(0~1)를 한 텐서로 합쳐 통째로 양자화하면 점수가 전부 0으로 반올림되는 함정을
  발견해 Conv만 양자화하는 방식으로 우회 (→ [STATUS.md 3장 함정 20](STATUS.md)).
- INT4·FP8은 검출 붕괴/실행 환경 부재로 기각 — nano+INT8이 유일하게 검증된 배포 조합
  (→ [STATUS.md — `C10a`](STATUS.md)).

## 5. 증류(distillation) — 해상도 대신 용량으로 정확도 보완

- 겨냥 문제: 야간 볼라드 `<4px` recall 0.319. 미탐 원인 분해상 58%는 `blind`(예측
  자체가 없음 · 증류로 못 고침), 33%는 `lowconf`(예측은 했는데 확신 부족 · 증류가
  겨냥할 수 있는 지점).
- 교사는 더 큰 `11m`/`11l`이 아니라 **같은 계열 `YOLO11s`**를 선택 — ① 이미 `11s`
  기준 실측 근거(day mAP50 +0.059, `<4px` recall +0.093)가 있고 ② 같은 YOLO11
  아키텍처라 ultralytics 특징 증류 훅이 그대로 걸리며 ③ 해커톤 일정상 검증된 최소
  단위부터 시도.
- 교사도 기존 인수분 가중치(`c4d_11s_640`, 주간 전용·별개 계보)를 재사용하지 않고
  **자체 데이터(`detect_v3`)로 새로 학습** — 그대로 쓰면 `c4e_s3_11n`이 이미 확보한
  야간 강점을 학생이 도로 잃을 위험이 있었다.
- 즉 **배포는 끝까지 `11n`·`640` 크기를 유지**하면서, 정확도만 더 큰 형제 모델
  (`11s`)의 지식으로 끌어올리는 전략 (→ [distillation_plan_20260829.md](distillation_plan_20260829.md)).
- ⚠️ 8/31 실행 결과, `own_night`(교사>학생)과 NightOwls `rec34`(학생>교사) 사이에
  우열이 뒤집혀 **최종 채택은 아직 `C11` 실기기 판정 대기 중**이다
  (→ [runpod_distillation_20260831.md](runpod_distillation_20260831.md)).

## 6. 남은 불확실성

- **`C11`/`C11b`(실기기 속도 계측) 미착수** — 640 고정 전제, 11n 단독 채택, 증류
  필요 여부 판단 전부가 이 계측 결과에 따라 재검토될 수 있다.
- 개발 PC는 15~25ms 구간을 판정할 수 없다(→ [STATUS.md 3장 함정 3](STATUS.md)) —
  위 표의 속도 수치(≈20.4ms 등)는 참고치이지 확정치가 아니다.

## 7. ✅ 최종 채택 — `c4f_distill_11n_640` INT8 (`generic` 프리셋, 2026-09-03 확정)

`outputs/quantization/bammasil_det_c4f_distill_11n_640_640-INT8/`의 `metadata.json`·
`README.md`(`export_onnx.py`·`quantize_onnx.py` 자동 생성)를 근거로 한다.

### 7-1. 모델 개요

| 항목 | 값 |
|---|---|
| 아키텍처 | Ultralytics **YOLO11n**(2.59M params) |
| 학습 방식 | **지식 증류** — 교사 `c4f_11s_640_teacher`(YOLO11s)로부터 학생 학습 (→ 5장) |
| 학습 데이터 | `detect_v3` (NightOwls 실야간 + AIHub bollard + StairNet, 3클래스) |
| 클래스 | `0 person` · `1 stairs` · `2 bollard` |
| FP32 원본 | `bammasil_det_c4f_distill_11n_640_640.onnx` (10.61MB, SHA256 `026543fd...`) |
| 이 산출물 | `..._INT8_generic.onnx` (3.15MB, SHA256 `47ab6fdd...`) |
| 내보낸 날짜 | 2026-08-31 |

### 7-2. 입출력 계약 (ONNX)

```
입력  images  : float32 [1, 3, 640, 640]   NCHW · RGB · /255 (mean/std 정규화 없음)
출력  output0 : float32 [1, 7, 8400]        cx,cy,w,h + person/stairs/bollard 점수(sigmoid 적용)
```

- 전처리: **letterbox 정사각(square)**, 회색 114 패딩
- NMS: **그래프에 없음** — 앱에서 conf 0.25 → xyxy 변환 → 클래스별 NMS(IoU 0.7) → letterbox 역변환
- FP32 판(`c4e_s3_11n`)과 **입출력 계약 완전 동일** — 앱이 고칠 것 없음

### 7-3. 양자화 사양

| 항목 | 값 |
|---|---|
| 방식 | QDQ static, **Conv 레이어만**(`op_types_to_quantize=["Conv"]`) — 헤드 산술은 FP32 유지 |
| 이유 | 전부 양자화하면 마지막 `Concat`(좌표+점수 결합)의 스케일 붕괴로 **검출 0건** 발생 (→ [STATUS.md 3장 함정 20](STATUS.md)) |
| 캘리브 | minmax · 159프레임(`data/test_real_data`, 야간 실촬영) |
| per-channel/per-tensor | per-channel(가중치) / QUInt8(활성) |
| 대상 런타임 | NNAPI · Core ML · ONNX Runtime CPU EP |
| 압축비 | 10.61MB → **3.15MB (3.37배)** |
| FP32 대비 정합 | 검출수 불일치 **0건**(7장 기준) · 좌표 최대오차 7.71px · conf 최대오차 0.109 |

⚠️ 스냅드래곤 계열은 별도 `qnn` 프리셋(3.04MB, per-tensor) 필요 — QNN EP(HTP) 전용, 실기기 그래프 적재 여부 미확인.

### 7-4. 성능 지표

### 8-5. `stairs` AP50이 낮은 원인 — 정량 분석 (2026-09-02)

`data/own_night/labels`의 stairs 라벨(class 1) 21박스를 직접 파싱해 박스가 프레임에서
차지하는 면적 비율을 실측했다. 기존 문서(→ [detection.md 8장](detection.md))가
정성적으로만 말하던 "StairNet 도메인 문제"를 수치로 확인한 결과다.

**핵심 발견 — 학습 데이터와 실제 테스트 데이터의 스케일이 크게 다르다**

| | StairNet(학습) | own_night stairs(실측, 21박스) |
|---|---|---|
| 박스가 프레임에서 차지하는 면적(중앙값) | **47.5%**(→ [detection.md 2-1](detection.md), 계단이 화면을 가득 채운 근접샷) | **약 3.0%** |
| 면적 10% 미만 박스 비율 | — | **71%**(21개 중 15개) |
| 면적 분포(정렬) | 항상 큼(근접) | 0.7~40.6%로 넓게 퍼져 있고 대부분 한 자릿수% |

즉 own_night 계단의 71%가 학습 때 본 것보다 **10배 이상 작은 크기**로 찍혀 있다.
StairNet은 "계단 앞에 서서 찍은 사진"만 있어 원거리·접근 중인 계단을 학습한 적이
없는데, 실제 보행 상황에서는 계단이 대부분 이 정도 작은 크기로 등장한다.

**왜 기존 진단 도구(폭 구간별 recall)로는 안 보였나** — `eval_own_night.py`의 GT
폭 구간 버킷(`<4px`/`4~8px`/`8~16px`/`>=16px`, 640 기준 **절대 픽셀** 높이)으로 보면
stairs 박스 21개가 전부 `>=16px` 버킷 하나에 몰려 recall 0.143으로 뭉뚱그려진다.
이 버킷은 볼라드처럼 물리적으로 작은 물체(4px 미만)를 잡으려고 만든 것이라, "절대
높이는 16px를 넘지만 프레임 대비로는 몇 %밖에 안 되는" 계단의 **상대적 스케일 문제**를
구분하지 못한다.

**종합 원인**

1. **주 원인 — 학습·테스트 도메인 스케일 불일치(이번에 정량 확인)**: StairNet은
   근접 사진만 있고, 실제 보행 시 계단은 훨씬 작게 보인다. 모델이 이 스케일 구간을
   학습한 적이 없다.
2. **보조 원인 — 라벨 품질**: 41장 재라벨링 전후로 `stairs` mAP50이 0.02~0.04 →
   0.08~0.20로 뛴 전례가 있어(→ [detection.md 9-12](detection.md)), 라벨 좌표
   정밀도도 일부 기여했다.
3. **볼라드의 `<4px` 문제와는 성격이 다르다**: 볼라드는 물리적으로 작은 물체(정보
   자체가 없음)인 반면, 계단은 "학습이 안 된 크기 구간"(정보는 있지만 이 스케일을
   훈련에서 못 봄)이다 — **증류·양자화 같은 모델 축 개선으로는 안 풀리고, `C2` 정식
   촬영에서 다양한 거리의 계단 표본을 넣는 것이 유일한 해법**이라는 기존 결론이
   이번 실측으로 더 명확히 뒷받침된다.
