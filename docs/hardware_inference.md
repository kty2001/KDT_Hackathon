## 0. 요약 (TL;DR)

- **TensorRT는 스마트폰에서 동작하지 않음** → 폰 단계는 QNN/NNAPI/Core ML 등 모바일 런타임으로 재정의. TensorRT는 확장 단계(Jetson)에서만 유효. ✅ *문서 정정 완료*
- YOLO 탐지만 놓고 보면 **720p·15FPS는 무난히 달성 가능**.
- 진짜 병목은 탐지가 아니라 **② 저조도 개선(dense 픽셀 연산)** 과 **골판지 하우징의 발열·지연**.
- 목표 FPS는 스택 정정 + ②단계 경량화로 **달성 가능한 범위**.

> **현재 상태**: ②·③ 모델이 아직 없어 **실측은 전부 미착수**다. 이 문서는 측정 전 예산 설계와 리스크 목록이며, 숫자는 모두 문헌·경험 기반 추정이다. 최우선 과제는 5장 체크리스트의 **② 단독 FPS 실측**.

## 1. 런타임 정정 — TensorRT는 폰에서 못 씀

TensorRT는 **NVIDIA GPU 전용** 런타임이다. 상용 스마트폰 AP에는 NVIDIA GPU가 없다.

| AP 계열 | GPU | NPU | 가용 런타임 |
|---------|-----|-----|-------------|
| 퀄컴 스냅드래곤 | Adreno | Hexagon | **ONNX Runtime(QNN/NNAPI EP)**, TFLite(GPU/QNN delegate), SNPE, NCNN/MNN |
| 삼성 Exynos | Mali | NPU | ONNX Runtime(NNAPI), TFLite(GPU/NNAPI) |
| 애플 A/M | Apple GPU | Neural Engine | **Core ML**, ONNX Runtime(CoreML EP) |
| **NVIDIA Jetson (확장 단계)** | CUDA GPU | — | **TensorRT** ✅ |

**조치** (✅ README 반영 완료, 원본 기획서 PDF는 수정 금지이므로 발표 시 구두 정정):
- 폰 배포 → **QNN / NNAPI / Core ML (모바일 NPU·GPU)**
- TensorRT → **Jetson 엣지 이식(확장) 단계에 한정**

> 참고: 개발 PC의 `onnxruntime-gpu`는 TensorRT EP를 인식한다. 이는 **학습·검증 환경의 편의**일 뿐 폰 배포 경로와 무관하니 혼동하지 말 것.

## 2. FPS 달성 가능성 분석

### 파이프라인 구성
```
①눈부심 억제 → ②저조도 개선(딥러닝) → ③YOLO 탐지 → ④엣지 강조 → 화면 렌더
```
FPS 예산은 이 전체를 합산해서 봐야 한다. YOLO 단독 성능이 아님.

### ③ YOLO 탐지 — 여유 있음 ✅
- YOLOv8n/v11n(nano) 320~640 입력 + INT8 양자화 → 최신 플래그십 NPU에서 30~60FPS, 중급기도 15FPS 확보 가능.
- 기획서대로 **탐지를 매 2~3프레임만 실행**하고 사이는 트래킹으로 보간하면 예산 추가 확보.
- **계단이 같은 모델에 통합됐다** ([data.md 4-3](data.md)). 클래스 1개 추가는 추론 비용이 사실상 0이므로 위 추정은 그대로 유효하다. 당초 검토했던 "계단 전용 모델 별도 구동" 또는 "고전 CV 계단 검출의 CPU 비용"이 예산에서 빠져 **③단계는 오히려 여유가 늘었다**.

### ② 저조도 개선 — 실질 병목 ⚠️
- **모든 픽셀을 매 프레임 처리하는 dense 연산**(720p 풀해상도 CNN)이라 객체탐지보다 무겁다.
- 양자화 내성도 탐지보다 약함(아래 3장).
- **FPS 예산의 대부분을 여기서 소비할 가능성** → 최우선 측정·경량화 대상.
- ⚠️ 위 서술은 **②를 딥러닝으로 구현한다는 전제**에 기댄다. 이 전제 자체가 아직 미검증이며, **고전 톤매핑으로 대체하면 병목이 소멸**한다. 방식 결정은 [data.md 2-3](data.md) 참고 — 본 문서의 실측이 그 판정 입력이다.

## 3. 양자화 전략 — 모듈별 차등 적용

| 모듈 | 권장 정밀도 | 근거 |
|------|-------------|------|
| ③ YOLO 탐지 | **INT8** (PTQ, 필요 시 QAT) | 탐지는 INT8에 강건, 정확도 손실 작고 NPU에 최적 |
| ② 저조도 개선 | **FP16 우선**, INT8은 화질 검증 후 | dense 복원은 INT8 시 밴딩·노이즈 발생 쉬움. 모바일 GPU FP16이 현실적 절충 |
| ① 눈부심 억제 / ④ 엣지 강조 | 고전 영상처리(양자화 무관) | GPU 셰이더/OpenCV 수준으로 처리 |

## 4. 골판지 VR(pass-through) 폼팩터 리스크

FPS 수치보다 하우징 자체가 만드는 문제가 성패를 좌우할 수 있다.

| 리스크 | 내용 | 대응 |
|--------|------|------|
| **발열·스로틀링** | 밀폐된 골판지 안에서 카메라+GPU+NPU 풀가동 → 수 분 뒤 thermal throttling으로 FPS 급락 | 벤치마크를 순간값이 아닌 **10분 지속 부하**로 측정. 통풍 구조·개구부 설계 |
| **지연(motion-to-photon)** | 눈앞 화면을 보며 걷는 pass-through라 카메라→처리→표시 지연이 크면 어지러움·보행 위험 | FPS와 별개로 **end-to-end latency 예산** 관리. 15FPS=66ms/프레임 + 처리 지연 합산 체감 |
| **스테레오 렌더링** | 카드보드는 화면 좌우 분할 + 배럴 왜곡 보정 필요, 같은 프레임 2회 렌더 | 표시단 렌더 비용 별도 계상. 시연 초기엔 단일 화면 모드로 검증 후 스테레오 적용 |
| **후면 카메라 가림** | 하우징이 후면 카메라를 막을 수 있음 | 카메라 개구부 구조 설계 |

## 6. 결론

목표 FPS(720p·15FPS)는 **① 스택을 모바일 런타임으로 바로잡고 ② 저조도 개선을 경량화하면 달성 가능한 범위**다.
단, "YOLO + ONNX + 양자화" 자체보다 **저조도 개선 병목 해소**와 **골판지 하우징의 발열·지연 관리**가 실제 성패를 가른다. 벤치마크는 반드시 **골판지 삽입 + 지속 부하 + end-to-end 지연** 조건으로 측정할 것.
