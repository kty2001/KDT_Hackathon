# 지식 증류(Knowledge Distillation)로 ③ 탐지 모델 고도화 — 계획서 (실행 보류)

## 0. 결론 요약

- **아직 실행하지 않는다.** `C11`(실기기 속도 계측)·`C5`(자체 야간 판정)이 먼저이고,
  증류는 그 결과에 따라 필요할 때만 쓰는 카드다 — 이 문서는 그때 바로 꺼내 쓸 수 있도록
  미리 세워 둔 순서·설계다.
- **겨냥하는 문제**: 야간 볼라드 `<4px`(볼라드 GT 의 21.8%) recall **0.319**. 원인 분해상
  미탐의 58%는 `blind`(예측 자체가 없음 · 증류로 못 고침), 33%는 `lowconf`(증류가 겨냥할
  수 있는 부분) — 증류를 쓰더라도 "다 고쳤다"가 아니라 "이만큼만 고칠 수 있다"로 보고할 것.
- **교사**: `detect_v3`(우리 자체 데이터, `c4e_s3_11n`과 동일)로 `YOLO11s`를 새로 학습한다.
  기존 외부 인수분 `c4d_11s_640`(주간 전용 · 별개 계보)은 재사용하지 않는다 — 그대로 쓰면
  `c4e_s3_11n`이 8/23 판정에서 확보한 야간 강점을 학생이 도로 잃을 위험이 있다.
- **코드 변경은 한 곳뿐**: `scripts/train_detect.py`에 `--distill-model`·`--dis` 인자
  추가. `ultralytics==8.4.106`(현재 잠금 버전)에 이미 네이티브 증류 지원이 있어 새 손실
  함수·콜백을 작성할 필요가 없다.

## 1. 왜 지금 실행하지 않는가

8/25 외부 리뷰(`docs/review_response_20260825.md`)가 증류를 이미 **"조건부 채택"**으로
정리해 뒀다 — 근거는 성립하지만(아래 2장) 선행조건 2건이 아직 안 풀렸다:

1. 🔴 **`C11`(실기기 속도 계측) 미착수.** 리뷰의 우선순위표(카드 2)는 "`11s`가 속도
   예산 안에 들어오면 증류 없이 `11s`를 바로 채택"이 먼저다. 증류(카드 4)는 "`11s`가
   예산을 못 맞출 때만" 쓸 카드다. `C11`은 폰 하우징(`P5`)에 막혀 있다(`docs/STATUS.md`).
2. 🔴 **모든 근거 수치가 주간뿐이다.** 이 프로젝트에서 반복된 함정(개발 val이 야간
   실효 성능을 못 봄)과 같은 구조. `C2`(자체 야간 촬영)가 아직 끝나지 않았다.

지금 실행하면 **아직 존재를 확인하지 못한 문제("`11n`속도가 진짜 필요한가")를 위해 미리
만드는 후보**가 된다. 그래서 이 문서는 실행 순서와 코드 변경 지점만 못박아 두고, 실제
실행은 `C11`·`C5` 판정 이후(또는 팀 판단으로 앞당길 때)로 미룬다.

## 2. 증류 근거 — 왜 기술적으로 성립하는가

같은 640 해상도에서 `YOLO11s`(9.43M)가 `YOLO11n`(2.59M)보다 day mAP50 +0.059
(0.753→0.812) · `<4px` recall **+0.093**(0.319→0.412) 높다(`c4d` 6런 비교,
`outputs/bammasil_results/bammasil_docs/benchmark_c4d.csv`). 즉 "교사가 학생보다 실제로
더 잘한다"는 증류의 전제가 성립한다.

`<4px` 미탐을 원인별로 나누면(`docs/review_response_20260825.md`):

| 원인 | `11n@640` 비중 | 증류로 되는가 |
|---|---|---|
| `blind`(예측 자체가 없음) | 58% | ❌ 입력에 정보가 없다 — 어떤 학습 기법도 못 고친다 |
| `lowconf`(예측은 했는데 임계 미달) | 33% | ✅ 증류가 겨냥하는 정확한 지점 |

해상도를 올린 `26n@960`에서는 같은 실패가 `lowconf` 쪽(60%)으로 옮겨가는 것도 확인됐다 —
모델이 "더 크면 보이긴 하는데 확신을 못 한다"는 뜻이라 증류의 논리와 방향이 맞는다.
ROI 크롭 실험(8/26 기각)도 부수적으로 같은 결론을 한 겹 더 쌓았다 — "정보량 0"인 크롭인데도
`<4px` recall이 +0.220 올라, 이 구간의 실패가 정보 문제가 아니라 **스케일 문제**임을 보였다
(`docs/detection.md` 9-9-3).

## 3. 왜 교사를 `YOLO11s`로 새로 학습하는가 (더 큰 모델이 아니라)

1. **이미 실측 근거가 있다** — 위 2장 수치가 전부 `11s` 기준이다. `11m`/`11l`이나
   NMS-free `26` 계열은 이 저장소 안에 그 정도의 실측 비교가 없어 "더 크면 더 낫다"는
   추정만 있고 검증이 없다 — 증거 없는 곳에 학습 시간을 먼저 쓰지 않는다.
2. **아키텍처 계보가 같다** — `11s`는 학생과 같은 YOLO11 계열(NMS 기반, `Detect` 헤드
   구조 동일)이라 ultralytics의 특징 증류 훅(4장)이 그대로 걸린다. `26` 계열은 NMS-free라
   헤드 구조가 달라 이미 앱 계약 사유로 배제된 계보이기도 하다.
3. **교사 학습 자체의 비용도 고려 대상이다** — 교사는 배포되지 않지만 학습 시간·증류
   단계의 forward pass 비용은 교사 크기에 비례한다. 해커톤 잔여 기간(마감 9월 초)을
   고려하면 검증된 최소 단위(`11s`)로 먼저 결과를 보고, 부족하면 그때 올리는 순서가 맞다.

## 4. 왜 기존 `c4d_11s_640`(이미 있는 가중치)이 아니라 새로 학습하는가

`c4d_11s_640`은 외부 인수분 계보 — **11K 축소셋·주간 전용**이다. 8/23 판정에서
`c4e_s3_11n`(우리 자체 3클래스 런)이 `c4d`를 이긴 이유가 정확히 **NightOwls 실야간 +
배경 음성 데이터**였다(`docs/STATUS.md` R4). 이 교사를 그대로 쓰면 학생이 `c4e_s3_11n`이
이미 확보한 야간 강점을 교사의 주간 편향 쪽으로 되돌릴 위험이 있다 — 즉 **증류가 되레
퇴보를 가르칠 수 있다.** 그래서 교사도 `c4e_s3_11n`과 **같은 데이터**(`detect_v3`,
경로는 `outputs/detect/c4e_s3_11n/args.yaml` 참고)로 새로 학습한다. 비용은 학습 1런
(약 100 epoch, patience 20)뿐이라 이게 유일하게 안전한 선택이다.

## 5. 실행 순서 (나중에 진행할 때)

### 5-0. 선행 확인
- `C11` 또는 `C5` 판정이 실제로 필요해졌는지(또는 팀이 시간상 앞당기기로 했는지) 먼저 확인.
- `detect_v3/data.yaml` 위치 확인 — `c4e_s3_11n/args.yaml`에 기록된 경로 그대로 쓴다
  (`docs/STATUS.md` 3장 함정 15 — Junction 없으면 "데이터 없음"으로 조용히 실패하니
  먼저 건다).

### 5-1. 교사 학습 — `YOLO11s` on `detect_v3`

```powershell
uv run python scripts/train_detect.py --model yolo11s.pt --data <detect_v3 data.yaml> \
    --imgsz 640 --name c4f_11s_640_teacher
```

`scripts/train_detect.py`는 기존 그대로 재사용(수정 불필요) — `--model`만 바꾸면 된다.
완료 후 `bammasil_weights/NOTE.md` 관례대로 **`results.csv` 최종 epoch 값을 지표로 쓰지
말고** `best.pt`를 `bollard_val_2146` 또는 `eval_own_night.py`로 재평가한 값을 공식
수치로 쓴다.

### 5-2. `scripts/train_detect.py`에 증류 인자 추가 (유일한 코드 변경)

설치된 `ultralytics==8.4.106`(잠금 확인됨)에 **네이티브 증류 지원**이 이미 있다 —
`ultralytics/nn/distill_model.py`의 `DistillationModel`(교사·학생 헤드에 forward hook을
걸어 특징+검출 결합 손실을 계산, 교사는 freeze, 내보낼 땐 학생만 남는다), `model.train()`의
`distill_model=`(교사 가중치 경로) · `dis=`(증류 손실 가중치, 기본 6.0) 인자로 그대로 쓴다.
**새 손실 함수·콜백을 작성할 필요가 없다** — `train_detect.py`에 두 CLI 인자
(`--distill-model`, `--dis`)를 추가해 `model.train(...)` 호출에 그대로 얹기만 하면 된다.
기존 인자 파싱 패턴(`argparse`, 기본값 `None`/`6.0`)을 그대로 따른다.

### 5-3. 학생 증류 학습

```powershell
uv run python scripts/train_detect.py --model yolo11n.pt \
    --distill-model outputs/detect/c4f_11s_640_teacher/weights/best.pt --dis 6.0 \
    --data <detect_v3 data.yaml> --imgsz 640 --name c4f_distill_11n_640
```

### 5-4. 평가 — 새 스크립트를 만들지 않고 기존 하네스 재사용

- `scripts/eval_own_night.py`(C5 하네스, 5축) — `c4f_distill_11n_640` vs
  `c4e_s3_11n`(현 최선 학생) vs `c4f_11s_640_teacher`(교사) 3자 비교. `C5` 라벨이 아직
  없으면 `scripts/eval_real_night.py`(라벨 없는 실촬영 7장+영상 5개)로 정성 비교만
  우선 수행한다.
- 특히 `<4px` 폭 구간 recall과 `lowconf`/`blind` 분해(2장과 같은 축)를 반드시 같이
  본다 — 증류가 정말 `lowconf` 33%를 건드렸는지가 이 실험의 핵심 판정 기준이다.

### 5-5. 배포 파이프라인 정합성 확인

증류 결과물도 순수 `YOLO11n` 구조이므로 기존 `scripts/export_onnx.py` →
`scripts/quantize_onnx.py` 파이프라인이 그대로 통과해야 한다 — 입출력 계약
`[1,3,640,640]→[1,7,8400]` 동일. 통과하면 INT8 판까지 만들어 `c4e_s3_11n` INT8 판과
같은 조건(`data/test_real_data`, conf 0.25, square letterbox)으로 비교한다.

### 5-6. 최종 채택 판단 — 이 계획서 범위 밖

`C11`(11s가 속도 예산 밖인지) · `C5`(야간 실측 우위)를 **둘 다** 통과해야 배포 후보로
올린다. 둘 중 하나라도 "그냥 `11s`를 쓰면 된다" 또는 "이득이 야간에서 안 재현된다"로
나오면 이 증류판은 `outputs/quantization`의 INT4·FP8 실험처럼 **기록으로만 남기고
채택하지 않는다.**

## 7. 검증 (실행 시점)

- 교사: `best.pt` 재평가 mAP50이 학습 로그 마지막 epoch 값과 다르다는 것을 확인하고
  재평가 값을 공식 수치로 기록(`NOTE.md` 관례).
- 학생(증류): `eval_own_night.py`(또는 `eval_real_night.py`) 결과를 `c4e_s3_11n`
  기준선과 나란히 비교 — 특히 `<4px` recall과 `lowconf` 비중 변화.
- 배포 정합성: `export_onnx.py`의 `parity_check`로 `.pt`↔ONNX 좌표오차 확인, 이어서
  `quantize_onnx.py`로 INT8 판까지 재현.
